# airlock — authenticating L7 gateway for exposing infrastructure to LLMs

**Status:** MVP
**Date:** 2026-06-11

## Problem

We want to let an LLM (or an LLM-driven agent) reach internal infrastructure —
HTTP services, and data stores like Redis and Postgres — without handing the
model raw, unrestricted access. The model is untrusted: its inputs can be
attacker-controlled (prompt injection), and it will happily issue any request
it can construct. Three risks dominate:

1. **Destructive/unsafe operations.** A raw Redis or DB connection exposes
   `DEL`, `FLUSHALL`, `SET`, arbitrary SQL, etc. The model must never be able to
   mutate or destroy state.
2. **Open egress / SSRF.** If the model can make the proxy connect to arbitrary
   hosts, it can reach cloud metadata endpoints (`169.254.169.254`), internal
   admin panels, or exfiltrate via outbound requests.
3. **Lack of accountability.** Every action the model takes must be
   attributable to a client identity and auditable after the fact.

## Design: a single authenticating L7 gateway

airlock is **one HTTP server** that is the *sole* entry point for the LLM side.
Nothing on the trusted side is reachable except through it. Each request flows
through a fixed pipeline:

```
request
  │
  ▼
[1] authenticate   ── Bearer token / API key ─► unknown/missing => 401
  │
  ▼
[2] route          ── METHOD+PATH => Operation ─► no match     => 404
  │
  ▼
[3] authorize      ── per-client default-deny allowlist ─► not listed => 403
  │
  ▼
[4] rate limit     ── per-client token bucket ─► over limit => 429
  │
  ▼
[5] execute        ── backend operation handler ─► outcome
  │
  ▼
[6] audit (structured slog: client, operation, decision, outcome) — at every exit
```

### [1] Authentication

Clients present a credential as `Authorization: Bearer <token>` or
`X-API-Key: <token>`. The gateway maps the token to a configured **client
identity**. A missing or unrecognized token yields **401** and is audited as a
denial with an `unknown` client id. Tokens live in configuration (file/env),
never in code.

### [2] Routing via explicit endpoint addressing

Every capability is an **Operation** with a stable id (e.g. `redis.get`), an
HTTP method, and a path (`GET /redis/get`). Operations are contributed by
**backends** registered in a registry and addressed explicitly by their route.
There is no wildcard/transparent forwarding: a path that maps to no operation is
a flat **404**. Selective routing is therefore trivial and total — the set of
reachable actions is exactly the set of registered operations.

### [3] Authorization — default deny

Each client carries an explicit **allowlist** of operation ids. Authorization is
a set-membership test: if the requested operation id is not in the client's
allowlist, the request is **403**. The default — for a new client, a new
operation, or any gap — is *deny*. There is no "allow all" escape hatch.

### [4] Rate limiting

Each client has a per-client **token bucket** (`rps` + `burst`). Requests that
would drain the bucket below zero are rejected with **429**. The clock is
injectable so the behavior is deterministic under test. Limiting is keyed by
client identity, so one noisy client cannot starve others.

### [5] Backends and curated data-store operations

Backends implement a small interface and contribute operations to the registry.

- **HTTP infra services** (future): reverse-proxy routes. The registry seam is
  in place; actual upstream TLS termination/proxying is out of scope for the
  MVP.
- **Data stores (Redis here; Postgres later)** are deliberately **not** exposed
  as raw TCP. Instead the gateway holds a **read-only engine credential** and
  exposes a hand-curated set of read operations. For Redis the MVP exposes
  `GET`, `SCAN`, `EXISTS`, and `TTL` only. The seam is a narrow `ReadClient`
  interface whose method set contains *no* write/destructive command — this is
  enforced by a reflection-based test, so a write path cannot be added by
  accident.

### [6] Audit logging

Every request — allowed or denied, at every exit point — emits one structured
`log/slog` record: client id, operation id, method/path, decision
(`allow`/`deny`), a reason on denial, and the HTTP outcome status. Denials log
at `WARN`, allows at `INFO`. This gives a complete, queryable trail.

## Why this beats a forward / transparent proxy

A forward or transparent TCP/HTTP proxy would let the model open connections and
speak the backend's native protocol. We reject that:

- **Data-store operation safety.** A transparent Redis/DB proxy that passes the
  wire protocol through cannot, in general, distinguish a safe `GET` from a
  destructive `FLUSHALL` or an arbitrary `EVAL`/SQL without re-implementing a
  protocol-aware firewall. airlock inverts this: the model never speaks the
  backend protocol at all. It calls a *curated HTTP operation*, and airlock
  constructs the backend command itself, from a fixed read-only vocabulary. The
  dangerous commands are not merely blocked — there is no code path that emits
  them.
- **No open egress ⇒ no SSRF / metadata risk.** Because routing is explicit
  endpoint addressing against a finite operation registry (not a destination the
  caller supplies), the model can never steer the gateway at an arbitrary host.
  The cloud metadata endpoint, internal admin services, and outbound
  exfiltration channels are simply not addressable.
- **Trivial, total selective routing.** "What can the model do?" is answered by
  enumerating the registry and each client's allowlist — both finite, explicit,
  and reviewable. A transparent proxy answers that question with "anything the
  backend protocol permits," which is the wrong default.

## Configuration

A JSON config file (path from `AIRLOCK_CONFIG`, with a few env overrides such as
`AIRLOCK_LISTEN`) defines: the listen address, the set of clients (id, token,
allowlist, rate limit), and backend definitions (e.g. the Redis address). See
`airlock.example.json`.

## Out of scope (MVP)

Postgres tool; real upstream TLS termination / reverse-proxying of HTTP
backends (registry seam only); multi-tenancy; web UI.
